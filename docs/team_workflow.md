## 2. 每个成员及其 Codex 的开工顺序

1. 读根目录 AGENTS.md、README 和本文，确认当前用户对应的角色。A/B 未绑定时，由当前用户自报角色；不要根据作者名单顺序推断。
2. 阅读对应任务卡及其引用的技术/数据/评估规范。历史 proposal 仅作参考，当前用户指令优先于历史规划。
3. 检查当前目录、Git 分支、未提交改动和已有代码，区分“文档设计”“已实现”“本地验证”“远程 GPU 验证”。
4. 实现任务使用自己的 checkout 与短分支。列出本次要改的文件、依赖的上游产物和验收方式后，在已授权范围内继续实现，不必每个常规步骤重复确认。
5. 缺少共享服务器或正式数据时，先完成 CPU 数据流、格式检查与小型测试夹具，不把整个任务停在等待 GPU 上。
6. 完成后提交清楚的交接记录：改了什么、如何运行、已检查什么、哪些仍未验证、下游要读哪些文件。

可交给 Codex 的任务模板见每张角色卡；模板中的第一批工作不等于授权立即启动长期付费训练。

## 4. 最小数据交接契约

详细定义以 [实现规范](implementation_spec.md) 和 [数据协议](data_protocol.md) 为准。B 负责把这些要求落成可运行的读写/验证器，各方共同审查。

| 产物 | 生产方 → 使用方 | 必须明确的内容 |
| --- | --- | --- |
| 图片与分区 manifest | B → 全员 | 稳定 image ID、相对路径、尺寸、split/group ID、源标注与文件哈希 |
| 分割标注与 GT 候选 | B → Liu Chunyu/A | 原实例 ID、八类 ID、保留源细类、mask、框、crowd/排除规则；GT 候选与预测候选分开命名 |
| 人工复核查询 | 全员标注，B 导出 → A/评价器 | query ID、image ID、完整文字、语言、唯一目标 ID、同义/反事实分组、split、复核状态 |
| 预测候选包 | Liu Chunyu → A/B | 候选 ID/顺序、类别、分割分数、原图框和 mask、decoder query ID、checkpoint 与解码配置哈希 |
| 特征缓存 | A → A/B 接口检查 | 同序候选 ID、图像/文本向量、实际 D、模型/processor revision、输入处理与缓存键 |
| 预测记录 | 各方法负责人 → B | query ID、method/run ID、选中候选或失败状态、输出 mask 引用、分数、候选来源 |
| 评价结果 | B → 全员 | 完整查询分母、逐条预测关联、指标/分组计数、误差类别、源码与 manifest 版本 |

约束：

- 八类项目 ID 是 1–8，分割训练内部 ID 是 0–7；转换显式记录，不能混用。
- 框是原图像素 `xyxy`，右下边界排他；mask 解码后是原图 `H×W`。跨环境优先用 COCO RLE JSON 或无损 mask 文件加相对引用，不交换框架专属 Python 对象。
- 图像为 RGB；候选顺序与特征索引一致。GT 候选 ID 可以关联源 annotation ID；预测 ID 不冒充 GT，评价关联单独保存。
- `target_instance_id`、人工目标类别、query type、复核标签只给训练/评价逻辑；推理不得读取这些答案字段。
- 候选为零、未输出、推理失败必须返回明确状态；不得删掉困难查询或把失败伪装成成功。
- 仅缓存冻结特征，不缓存仍在训练的残差/空间结果；接口版本或候选配置变化时生成新缓存。
- JSON schema 版本、分类映射、数据划分和候选解码变更须更新依赖记录；不能在相同路径悄悄换内容。

## 6. 查询标注与交叉复核

B 分配互不重复的图片批次并维护记录，三人各承担一部分描述。建议复核轮转：Liu Chunyu 写 → A 复核，A 写 → B 复核，B 写 → Liu Chunyu 复核。先让复核者只看图片与描述选择目标，再比对实例 ID，不自写自审。

不唯一、翻译改变含义、属性不可见、mask 无效等记录进入修订队列；没有完成复核不能标为 accepted。测试描述必须遵守独立人工撰写要求；用 Codex 生成后人工修改须如实记录来源，不改记为独立人写。

划分按图片/重复组先确定，同图翻译、改写和反事实始终留在同一分区。全员标注时不查看模型预测来改写测试难例。B 维护统计和格式，成员对自己撰写及复核的内容负责。

## 7. AutoDL 与多 Codex 同时工作

平台已选 AutoDL；单张 24GB GPU 是规划起点，实际实例、SSH、显卡、费用预算与环境尚未确认。已有私有镜像的基础信息是 Ubuntu 22.04 / Python 3.10 / PyTorch 2.1.0 / CUDA 12.1，但不证明镜像内实际环境或 CUDA 扩展可用。先只读检查，不先批量升级或重置。

### 7.1 建议目录（尚未创建）

```text
/root/autodl-tmp/fashion-grounding/
  workspaces/segmentation/       # Liu Chunyu 独立 clone
  workspaces/grounding/          # A 独立 clone
  workspaces/data_eval/          # B 独立 clone
  shared/raw/                   # 原始数据，各方只读使用
  shared/processed/<version>/   # B 发布的不可变数据包
  shared/candidates/<run_id>/    # Liu Chunyu 发布的候选包
  shared/features/<cache_id>/    # A 发布的特征缓存
  shared/weights/               # 固定公开权重与哈希
  runs/<role>/<run_id>/          # 独立日志、checkpoint、预测
  coordination/                 # GPU 占用登记与锁
```

这些目录是团队约定；共享 root 账号下不构成权限隔离。每人使用自己的 SSH 密钥，Git 提交使用本人身份，不能共用账号 token、私钥或把连接凭据提交公开仓库。GitHub 协作者权限不等于 SSH 权限。

### 7.2 环境与进程

- `segmentation` 环境由 Liu Chunyu 维护；`grounding` 环境由 A 维护；B 需要时建立独立 `data_eval` 环境。环境名是建议名，先检查旧镜像已有环境并记录真实名称/路径。
- 同一服务器共用驱动，不同环境可有不同 Python/PyTorch 依赖；分割自定义算子另检查编译工具链。不要把未经验证的版本组合写成已成功环境。
- 各角色保存自己的依赖记录与实际命令。需要改共享环境时先与正在使用它的人协调，优先新建环境验证，不在别人训练时执行全量升级。
- 每人用独立命名的 tmux 会话，长任务写日志和恢复点；SSH 断开不等于任务停止，聊天结束也不等于 Codex 持续监控。
- 数据、候选、特征通过文件交接。单卡先采用分阶段运行，不要求分割和图文模型同时驻留 GPU。

### 7.3 GPU 排队与操作权限

运行前同时检查 `nvidia-smi`、团队占用记录和已登记的长任务。建立一把共用的系统文件锁（例如 `flock`）作为 GPU 任务入口，锁内再次确认资源；CPU 数据处理不持 GPU 锁。单纯创建两个不同 tmux 会话不会隔离显存，看到瞬间空闲也不能认定无人占用。

登记至少包括角色/实际成员、run ID、代码 commit、tmux 会话/PID、启动时间、预算上限、输出目录和状态。锁文件本身留存不代表锁仍被进程持有；过期记录应核实进程后修正。共享锁包装脚本尚待实现，实施前由 Liu Chunyu 协调明确排队，禁止多方抢跑。

- 启动收费实例、长期训练、扩容或改变计费方式，需要当前用户已授权的任务范围及预算；已有有效授权无需重复询问。本文分工不是新的消费授权。
- 可以在已授权任务内完成常规实现和检查；不得结束别人的进程、重置/释放实例、覆盖共享数据或擅自关机。
- 自动关机只有在实例负责人明确授权且确认没有其他成员任务时使用，不作为每个训练脚本的默认动作。
- 发布共享产物先写到自己的运行目录，检查通过后再交接到版本化路径；不覆盖旧版本。大数据和权重不进 Git，重要结果另行备份。
